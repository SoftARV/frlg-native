# Spike 0001 — Deriving the relocation table

**Question:** [ADR 0006](../adr/0006-rom-supplied-data.md) ships no game data and instead loads the
player's ROM into the cart region, relocating the pointers embedded in it. That relocation table
was recorded as *unproven*. Can it be derived mechanically, and is it complete?

**Verdict: proven, end to end, against a byte-identical retail ROM.** Two findings changed the
plan, both cheap to absorb now and expensive at Phase 7.

## Method

Relink the ROM with relocations preserved, read them back, and check every record against the bytes
of the ROM it describes:

```sh
rm -f pokefirered.gba pokefirered.elf
make compare LDFLAGS="-Map ../../pokefirered.map --emit-relocs"
arm-none-eabi-readelf -rW pokefirered.elf
```

`agbcc` was built and installed to make the byte-matching build available — see
[finding 2](#finding-2-the-manifest-must-come-from-the-byte-matching-build).

## Results

The build reproduces the retail cartridge exactly — SHA-1
`41cb23d8dccc8ebd7c649cd8fbb58eeace6e2fdc`, matching `firered.sha1` — and **`--emit-relocs` leaves
the ROM byte-identical**, so the manifest is generated by a build that simultaneously verifies
itself against the real cartridge. That property is what makes the whole approach trustworthy.

`--emit-relocs` preserves exactly the sections that matter — `.rel.rodata`, `.relscript_data` and
`.rel.data` — yielding **49,547 pointers embedded in ROM data**, each carrying its ROM offset,
target symbol and addend.

The table is complete and self-consistent:

| Check | Result |
| --- | --- |
| Relocation offsets falling inside the ROM image | **49,547 / 49,547** |
| Sites whose stored word is a valid GBA address | **49,547 / 49,547 (100.00%)** |
| Negative addends | 0 |

Offsets are usable as ROM addresses directly, with no translation.

## Finding 1: one pointer in nine is a function pointer

Classifying each target by address, against the matching build's section map (`.text` is
`0x08000000–0x0815F9B4`, data runs above it, RAM sits below `0x08000000`):

| Target | Count | Share | How the importer resolves it |
| --- | --- | --- | --- |
| Data | 43,427 | 87.65% | `cart_base + (rom_addr - 0x08000000)` |
| **Code** | **5,525** | **11.15%** | address of the **native** function of that name |
| RAM variable | 595 | 1.20% | address of the **native** variable of that name |

This invalidates the naive reading of ADR 0006 — "point every data symbol into the loaded ROM image
and be done". Native code does not live in the ROM image, and command tables, callback tables and
script dispatch all store pointers to it.

It is not fatal, because each record names its target *symbol* and our binary contains a native
definition for every code and RAM symbol. The importer needs two inputs: the relocation table, and
a symbol-name → native-address table generated from our own link. **Import is therefore a patch
pass over the loaded image** — 49,547 words rewritten once at first boot — not merely symbol
binding.

It also **independently reconfirms [ADR 0003](../adr/0003-pointer-width.md)**: native function
addresses must fit the ROM's 4-byte slots, so 64-bit needs the data regenerated with wider slots,
exactly as Phase 11 already assumed. Two decisions reached separately agree.

## Finding 2: the manifest must come from the byte-matching build

The manifest is only meaningful if its addresses describe the ROM the *player* supplies. Addresses
from the `MODERN=1` build do not, and the gap is not subtle:

| | matching (`agbcc`) | modern (GCC) |
| --- | --- | --- |
| `.text` size | `0x15F9B4` | `0x16FD90` |
| `script_data` base | `0x0815F9B4` | `0x0816FD90` |
| embedded data pointers | 49,547 | 61,137 |

`ld_script.ld` is 42 KB and pins object placement in 512 explicit entries to reproduce retail;
`ld_script_modern.ld` is 2 KB of wildcards. A modern `.text` is larger, so everything after it
shifts — **66,524 bytes** for `script_data`. A manifest built from the modern ROM would describe
addresses no cartridge has.

So `agbcc` is a hard prerequisite of Phase 7, not the optional convenience the roadmap first called
it. It has been built and installed, and the matching build verified.

## What this changed

- `ARCHITECTURE.md` §5.1 and §5.3: import is a patch pass; the manifest carries a relocation table
  plus a native symbol table, and must come from the matching build.
- `ROADMAP.md`: the "agbcc is not on the critical path" assessment was wrong and is corrected.
- Nothing here blocks Phases 1–6, which use the developer data path.

## Finding 4: the generators have to read that build's layout too

Added 14 Aug 2026, when the matching manifest was first built and run.

Finding 2 says the manifest must come from the matching build. What it does not say is that the
tools generating it carried the *modern* layout as an assumption, in two places, and neither failed
loudly.

**Where code ends is not a number.** Both generators classified an address as code by testing it
against a single `.text` end. The matching build puts the library routines in their own `lib_text`
section which sits **above** `script_data`, so every symbol in it was filed as ROM data and bound
into the cart image. The game called one before the first frame -- `rfu_setTimerInterrupt`, from
`InitRFU` -- and jumped into its own data:

```
agb_cart+0x1e07d0  [0x8c88830]
InitRFU+0x2f
AgbMain+0x67
```

`0x081e07d0` is inside `lib_text` (`081dbd34`–`081e9f10`). 57 symbols were misfiled this way.

**Which sections hold pointers is not a list either.** `gen_relocations.py` named the relocation
sections it would read: `.rel.data`, `.rel.rodata`, `.relscript_data`. The matching build keeps the
music in `song_data`, with its own `.relsong_data`, and `lib_rodata` with `.rellib_rodata` — neither
of which that list mentions. Every pointer the sequencer follows stayed a cartridge address, and the
result was a game that **rendered perfectly and made almost no sound**: 90 non-silent frames against
2,178. It is the quietest possible failure, and nothing crashed.

Both are now read from the ELF's own section flags, in `tools/elfsections.py`, shared so the two
generators cannot disagree: executable sections are code, allocated non-executable ones hold data.
Relocations went from 49,552 to **54,128** once the music was included.

**What this says about the phase.** The port has read modern-built ROM data for six phases, and it
was right every time — against a layout no player has. Both defects were invisible until the
matching manifest was actually run, one loud and one silent, and only the loud one would have been
found by booting the game. **The check that mattered was replaying a trace and comparing the audio
stream byte for byte** against the dev build; 48,380,416 bytes, identical, is what says the data is
being read correctly rather than merely plausibly.
